![Model Settings](/images/model-settings.png)

holaOS ships with a default model setup. In most cases, you do not need to edit `runtime-config.json` by hand, because the desktop app already exposes the main configuration surfaces for provider connection, managed model catalogs, background tasks, recall embeddings, image generation, and web search.

This page is the configuration reference for operators and builders. For the Electron IPC path, runtime model-catalog refresh flow, queued `thinking_value` handoff, and other execution internals, continue into [Desktop Internals](/docs/contribute/desktop/internals) and [Runtime APIs](/docs/contribute/runtime/apis).

The baseline defaults are:

- default model: `openai/gpt-5.4`
- built-in fallback provider id when no configured default provider applies: `openai`

## Supported provider styles

The OSS runtime supports the following provider kinds:

| Provider kind | Best fit | Notes |
| --- | --- | --- |
| `holaboss_proxy` | holaOS-managed setups | Uses the holaOS runtime binding and managed model catalog instead of a local seed list. |
| `openai_compatible` | OpenAI-style APIs | Best when you already have an OpenAI-style endpoint. Covers OpenAI, Ollama, MiniMax, and many self-hosted compatible APIs. |
| `google_compatible` | Gemini via the Google OpenAI-compat path | Uses the Google compatibility surface instead of the generic OpenAI-compatible routing path. |
| `anthropic_native` | Anthropic accounts and native workflows | Good when you want the provider's own integration path. |
| `openrouter` | Model experimentation and broad access | Useful when you want to swap models without changing the rest of the setup. |

Desktop currently exposes only holaOS Proxy in `Settings -> Model Providers`. The broader provider kinds below still describe lower-level runtime capabilities and legacy config shapes, but they are no longer first-class desktop provider choices.

## In-app setup

holaOS already provides model configuration in the desktop app:

- open `Settings -> Model Providers`
- connect holaOS Proxy
- use the `Background tasks` panel to choose one connected provider and model for recall selection, finalization, and other background LLM tasks
- use the `Recall embeddings` panel to leave vector-assisted recall on `Automatic` or choose an explicit embedding-capable provider and model
- use the `Image generation` panel to choose an image-capable provider and model for runtime image generation
- use the `Defaults` panel to leave `Subagent model` on `Follow composer` or choose a fixed override for hidden delegated and scheduled subagent runs
- use the `Web search` panel to choose Holaboss Search or Exa and provide a search API key when needed
- saved changes update `runtime-config.json`, and the chat model picker uses the configured provider models

holaOS-managed sessions can inject managed background, embedding, and image defaults through the runtime binding. The desktop UI now assumes holaOS Proxy is the only provider surface and derives its model suggestions from the managed catalog plus the shipped Holaboss fallback metadata.

## Catalog-driven chat models

The current desktop no longer treats chat models as only freeform strings.

- The shipped fallback catalog in `apps/desktop/shared/model-catalog.ts` now describes holaOS Proxy models only.
- Signed-in holaOS-managed sessions can also fetch a managed runtime model catalog from the control plane.
- The desktop merges that managed catalog with the locally persisted `runtime-config.json` and exposes the result as `providerModelGroups` in the runtime-config snapshot.
- Managed defaults for background tasks, embeddings, and image generation are also carried with that snapshot as `defaultBackgroundModel`, `defaultEmbeddingModel`, and `defaultImageModel`.

In practice, that means the model picker and settings UI are both catalog-aware:

- `Settings -> Model Providers` uses the catalog to seed provider defaults and suggestions.
- The chat composer uses the resolved provider groups to show only the models that are actually available for the current runtime.
- Deprecated or unsupported model ids are filtered before they reach the renderer.

## Reasoning effort in chat

Reasoning effort is selected in the chat composer, not in `runtime-config.json`.

The current flow is:

1. select a chat model in the composer
2. if that model advertises `reasoning: true` and has non-empty `thinkingValues`, the composer shows a `Thinking` selector
3. the desktop remembers the last selected value per resolved model locally
4. when the message is queued, the desktop sends both `model` and `thinking_value` to `/api/v1/agent-sessions/queue`

That `thinking_value` is run-scoped metadata. It does not become a new global default model setting.

## Current shipped reasoning-value sets

The shipped fallback catalog currently exposes these reasoning controls:

| Provider / model | Reasoning values |
| --- | --- |
| `holaboss_model_proxy/gpt-5.4` | `none`, `low`, `medium`, `high`, `xhigh` |
| `holaboss_model_proxy/gpt-5.5` | `none`, `low`, `medium`, `high`, `xhigh` |
| `holaboss_model_proxy/gpt-5.3-codex` | `low`, `medium`, `high`, `xhigh` |

The managed holaOS catalog can provide explicit reasoning metadata. If it does not, the desktop falls back to the shipped Holaboss proxy metadata for known GPT-5 family models.

## Customization mode

You can configure the runtime in either of these modes:

- legacy or proxy shorthand
  - set `model_proxy_base_url`, `auth_token`, and `default_model`
- structured provider catalog
  - define `providers` and `models`, then set `runtime.default_provider` and `runtime.default_model`

Runtime URL behavior stays consistent across both modes:

- if `model_proxy_base_url` is a proxy root, runtime appends provider routes such as `/openai/v1` or `/anthropic/v1`
- direct mode is enabled when you provide a provider endpoint
- OpenAI-compatible direct providers typically use a `/v1` endpoint, for example `https://api.openai.com/v1`
- Google-compatible direct providers use the Gemini compatibility root, for example `https://generativelanguage.googleapis.com/v1beta/openai`
- Anthropic native direct providers should use the root host, for example `https://api.anthropic.com`
- known provider hosts normalize as needed, including Gemini host roots to `/v1beta/openai`

## Where the runtime reads model config

The runtime resolves model settings from:

1. `runtime-config.json`
2. environment variables
3. built-in defaults

By default, `runtime-config.json` lives at:

- `${HB_SANDBOX_ROOT}/state/runtime-config.json`

You can override that path with:

- `HOLABOSS_RUNTIME_CONFIG_PATH`

## Important settings

- `model_proxy_base_url`
  - legacy or proxy base URL root
- `auth_token`
  - proxy token sent as `X-API-Key`
- `providers.<id>.base_url`
  - direct provider endpoint
- `providers.<id>.api_key`
  - direct provider credential
- `runtime.background_tasks.provider`
  - provider for recall selection, finalization, and other background LLM tasks
- `runtime.background_tasks.model`
  - model id used for that background provider
- `runtime.subagents.model`
  - optional fixed model token for hidden subagent execution; when unset, subagents use the current composer model if one is available
- `runtime.recall_embeddings.provider`
  - optional embedding-capable provider used for vector-assisted recall candidate narrowing
- `runtime.recall_embeddings.model`
  - optional embedding model id used for recall embeddings
- `runtime.image_generation.provider`
  - provider used for runtime image generation
- `runtime.image_generation.model`
  - image model id used for runtime image generation
- `web_search.provider`
  - provider used by the native `web_search` runtime tool
- `web_search.providers.<id>.base_url`
  - search endpoint URL
- `web_search.providers.<id>.api_key`
  - optional search provider credential
- `runtime.default_provider`
  - configured default provider for unprefixed model ids
- `runtime.default_model`
  - default model selection
- `HOLABOSS_DEFAULT_MODEL`
  - environment override for the default model

There is no `runtime.thinking_value` field. Reasoning effort is chosen per run in the chat composer and queued with the session input.

## Background task provider defaults

The current built-in background task defaults are:

- `holaboss_model_proxy`: `gpt-5.4`

## Recall embedding defaults

When `Recall embeddings` is left on `Automatic`, runtime chooses the first configured provider that has a built-in embedding default. If you configure it explicitly, the current built-in embedding defaults are:

- `holaboss_model_proxy`: `text-embedding-3-small`

## Image generation provider defaults

The desktop currently exposes image generation only for the providers that can resolve an image-capable model in the shipped UI:

- `holaboss_model_proxy`: managed catalog / runtime-binding defaults when available

There are no additional desktop-configurable provider surfaces for image generation.

## Web search providers

The native `web_search` tool reads a top-level `web_search` block from `runtime-config.json`. If that block is absent, the runtime keeps the legacy behavior and uses hosted Exa MCP without authentication.

The desktop currently exposes:

- `holaboss_search`
  - default endpoint: the runtime binding's control-plane base URL plus `/api/v1/search/web`
  - production fallback endpoint: `https://api.holaboss.ai/api/v1/search/web`
  - API key is optional when the runtime has a signed-in Holaboss binding
- `exa`
  - default endpoint: `https://mcp.exa.ai/mcp`
  - API key is optional for the hosted MCP path, but can be provided for your own Exa quota

The runtime also accepts legacy config keys `webSearch` and `search`, but the desktop writes the canonical `web_search` key.

## Model string format

Use provider-prefixed model ids when you want to be explicit:

- `openai/gpt-5.4`
- `anthropic/claude-sonnet-4-6`
- `openrouter/deepseek/deepseek-chat-v3-0324`

The runtime also treats unprefixed `claude...` model ids as Anthropic models. If a model id is unprefixed and does not start with `claude`, the runtime first tries the configured default provider. If no configured default provider applies, it falls back to `openai/<model>`.

## Local model servers

holaOS can use a model server that is already running on this machine or on the local network: Ollama, LM Studio, llama.cpp `llama-server`, MLX, vLLM, SGLang, or anything else that speaks the OpenAI chat completions API. holaOS does not install engines or download models; start the server yourself first.

### Find and register a running server

The runtime checks the usual ports (11434, 1234, 8080, 8000, 30000) when it starts and every 30 seconds after that. A server it finds is registered automatically and its models appear in the chat model picker. When the server's model list changes, the registration is updated. To turn this off, set `"local_models": { "auto_detect": false }` in `runtime-config.json`, or set `HOLABOSS_LOCAL_MODEL_AUTODETECT=0`.

For a server on another port or machine, ask the agent ("use the model I have running in LM Studio"), or call the runtime directly:

```bash
# list servers on the usual ports (11434, 1234, 8080, 8000, 30000) with their models and context windows
curl http://127.0.0.1:<runtime-port>/api/v1/local-models/discover

# add one, so its models appear in the chat model picker as <provider>/<model>
curl -X POST http://127.0.0.1:<runtime-port>/api/v1/local-models/register \
  -H 'Content-Type: application/json' \
  -d '{"base_url":"http://127.0.0.1:1234/v1"}'
```

The agent has the same operations as the `local_models_discover` and `local_models_register` tools.

Registration writes a provider and its models into `runtime-config.json`:

```json
{
  "providers": {
    "local_lmstudio": {
      "kind": "openai_compatible",
      "base_url": "http://127.0.0.1:1234/v1",
      "api_key": "local",
      "local": true
    }
  },
  "models": {
    "local_lmstudio/qwen/qwen3-8b": {
      "provider": "local_lmstudio",
      "model": "qwen/qwen3-8b",
      "context_window": 32768,
      "input_modalities": ["text"]
    }
  }
}
```

You can also write this by hand. A provider is treated as local when it sets `"local": true`, uses kind `local`, or its base URL host is `localhost`, `127.0.0.0/8`, `::1`, `*.local`, `host.docker.internal`, or a private IPv4 range. For local providers:

- a base URL without a path gets `/v1` appended (`http://localhost:8080` → `http://localhost:8080/v1`)
- `api_key` is optional, and cloud API keys from the environment are never sent to them
- model ids may contain `/` (`qwen/qwen3-8b`, `mlx-community/...`)
- the context window comes from `context_window` (default 32768) and output is capped at `max_tokens`, or half the context up to 16384
- input is text-only unless `input_modalities` includes `"image"`

### Context window

holaOS sends its instructions and tool definitions with every request (about 14,000 tokens), so a local model needs a context window of at least 16,384 tokens; 32,768 or more is recommended. Before each run the runtime asks the server what context it is actually serving (llama.cpp `/props`, Ollama `/api/ps`, LM Studio `/api/v0/models`, vLLM `/v1/models`), records it, and stops with instructions if it is too small:

- llama.cpp: restart `llama-server` with `-c 32768`
- Ollama: set `OLLAMA_CONTEXT_LENGTH=32768` and restart Ollama, or use a Modelfile with `PARAMETER num_ctx 32768`. Ollama serves models with a small default context and silently truncates longer prompts, so this matters even when the model itself supports a long context.
- LM Studio: reload the model with a larger Context Length
- vLLM: `--max-model-len 32768`

For Ollama and LM Studio, a model that is not loaded yet is loaded first so its real context can be read.

If a model does not respond, check the server directly first:

```bash
curl http://127.0.0.1:1234/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"qwen/qwen3-8b","messages":[{"role":"user","content":"Reply with exactly: OK"}],"temperature":0}'
```

## Environment overrides

```bash
export HOLABOSS_MODEL_PROXY_BASE_URL="https://your-proxy.example/api/v1/model-proxy"
export HOLABOSS_SANDBOX_AUTH_TOKEN="your-proxy-token"
export HOLABOSS_DEFAULT_MODEL="anthropic/claude-sonnet-4-6"
```

These environment variables override the file-based values above. `sandbox_id` is still the current field name in `runtime-config.json`.
